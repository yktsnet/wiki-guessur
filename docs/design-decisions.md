# Design Decisions

[README](../README.md) の Design Decisions に対する全文。判断の過程ごと残す。

## 素材: cirrussearch ダンプの直接パース

採ったのは Wikimedia の cirrus_search_index ダンプ（jawiki、14シャード bz2・約8.2GB）を直接読む方式。

検討した代替は3つ。Hugging Face の前処理済み jawiki データセット群は本文抽出の手間が省けるが、リンク情報を持たない。wikipedia-utils は被リンク「数」までは取れるがリンクグラフそのものは作れない。Wikipedia API で必要分だけ取る方式は軽いが、生きた Wikipedia は日々変わるため、同じシードでも取得時期で中身がずれる。

このタスクはダミー候補を「クエリ記事にリンクしている記事」から採る。クエリはシードごとに全記事の母集団から引き直すので、どの記事の言及者が必要になるかは選ぶまで分からない。全記事の発リンクと本文を一度に含み、wikitext パーサも不要な cirrussearch ダンプが、要件をひとつのファイル群で満たす唯一の選択だった。

なお旧 `other/cirrussearch/` は 2026年1月に廃止されており、後継の `other/cirrus_search_index/`（週次・シャード分割）を使う。

## 版の固定: 変動要因はシードだけにする

ダンプの版は一度選んだら `config.toml` に日付で固定する（20260712）。頑健さ評価の本体は「シードを変えてコーパスを引き直したときの MRR の分布」であり、素材側まで動くと、観測された揺れがサンプリング由来か素材由来か切り分けられなくなる。

## 配布の3層構造: 利用者に 9GB を要求しない

リポに置くのはコードと結果だけ。生成済みコーパス（1シード数十MB）は Releases に添付し、9GB のダンプは Wikimedia から各自取得とする。

利用者の大半は結果を読むか、自分の手法を足して既存コーパスで評価したい人であり、それに必要なのはコーパスまでで足りる。ダンプが要るのは生成工程を自分でやり直したい人だけで、その経路も `fetch` / `generate` として残す。Wikipedia 本文の再配布は CC BY-SA の帰属表示と同ライセンス継承で成立する。

ダンプは生成が終われば消してよい一時素材であり、キャッシュ扱い（gitignore）にしている。

## 評価器の中の TF-IDF: 次元をクエリ記事名の n-gram に限定する

文字 n-gram TF-IDF のコサイン類似度は、コーパス全体の n-gram 辞書を作ると数千万次元になり、標準ライブラリ縛りの数式手法には重すぎる。類似度計算に寄与するのは記事名側に現れる n-gram だけなので、DF の集計をその語彙（5,000記事名で数万 n-gram）に限定した。計算結果は等価のまま、辞書がメモリに収まる。

## 完全一致ペナルティの棄却（仮説の反証）

当初は「ダミーは正解記事にリンクして言及する側なので記事名を含みやすく、定義文を失った正解は名乗れない」というねじれを想定し、完全一致をペナルティにする設計だった。診断統計がこれを反証した。実測では正解本文の65%が自分の記事名を含み（平均4回。Wikipedia 記事は本文中で自分の名前を繰り返す）、ダミーは35%（平均0.5回。リンクのアンカー表記はパイプや活用で記事名と一致しないことが多い）。ねじれは逆向きで、「名前を最も呼ぶ文書こそ正解」がこのコーパスの実態だった。

初回生成（seed 0 の train 分割）での係数グリッドフィットでも、ペナルティ・ボーナスどちらの向きでも MRR が下がり、最良は補正なしだった。言及回数の情報は記事名の文字 n-gram 類似度が既に内包しており、補正項は二重計上の雑音になる。数式手法は「記事名の文字 n-gram TF-IDF コサイン類似度」単体で確定し、以後係数は固定する（分布変化への弱さをそのまま観測する縛り）。

仮説が外れた過程ごと残すのは、診断統計を先に取る手順の価値の実例だから。ベンチマークの前提は主張する前に測る。

## 生成の決定性: クエリ単位のシード派生 RNG と reservoir sampling

ダミー候補の選択は、ダンプを1周しながらクエリごとの reservoir sampling で行う。乱数はグローバルな RNG を共有せず、`hash(seed, クエリ記事名, ...)` から都度導出する。これで（1）ダンプの読み順が固定なら出力が完全に決定的、（2）全候補を貯めてから選ぶ方式で起きるメモリ爆発（最悪で数十万文書分の本文）を回避、の両方が成立する。

## 学習手法: LightGBM の lambdarank

タスクは候補の順位付けなので、二値分類ではなくランキング学習（lambdarank）を使う。GBDT 系で lambdarank を持ち、再生成のたびの再学習が数秒で終わる LightGBM を選んだ。scikit-learn の GBDT は依存が軽いがランキング目的関数がない。自前実装は依存ゼロにできるが、本題は手法の比較であって GBDT の再発明ではない。

## 評価の公平性: 全手法を同じ test 分割で測る

数式手法は学習しないので全クエリで測れるが、学習手法と数字を並べるため、シード決定的な train/test 分割の test 側だけで全手法を測る。手法間の差にデータの差が混入しない。

## 難易度ノブは評価時のサブサンプルで実装する

候補数ノブ（k 上限）は、コーパスを作り直すのではなく、既存コーパスの候補列を評価時に間引く形にした。ダンプの再走（1回35分）なしで掃引でき、同じ文書集合の上で k だけが変わるので比較も純粋になる。間引きでは候補の保存順を保つ。正解を先頭へ移す実装は、スコア同点時に安定ソートが先頭を優遇して MRR を水増しする（実測で+0.005 の偏りが出た）。この検算には「k=10 は実質無制限なので本表と一致するはず」という恒等式が使え、テストにも残した。除去文量ノブ（冒頭以外の除去範囲を変える）は再生成が必要なため保留している。

## LLM 層の閾値・サンプリングは測ってから決める

僅差閾値は事前に決めず、seed 0 の実測（スコア差分布と帯別正答率）から決めた。正規化スコア差 0.1 未満で test の9〜12%・当該帯の正答率42%と、「ほぼ差が付いていない帯」だけを切り出せる。無料枠（15 RPM / 500 RPD）の制約から対象の 1/10 をシード決定的にサンプリングし、サンプル実測と全体外挿の推定を分けて記録する。A/B の提示順もシード決定的に反転し、LLM の位置バイアスを均す。API キーは環境変数のみ、リポには書かない。

seed 0〜4 の5シード実測でも、この閾値・サンプリング設計は再現した。LLM層はformula側で平均+0.0145、gbdt側で平均+0.0155とどちらのシードでも底上げし、LLM正解選択率は formula 僅差で80〜91%、gbdt 僅差で63〜75%と、土台が強いほど下がる傾向が一貫して出た。土台のスコアラーが多くの手がかりを使い切るほど、残る僅差ケースは本質的に紛らわしい問題として残るためと考えられる。

## LLM は手法ではなく層

LLM を独立した4つ目の手法にせず、基礎スコアラーの上位2候補が僅差のときだけ差し替える再判定層とした。どのケースが僅差かを決めるのは下のスコアラーなので、LLM 層の効果は土台の性能に依存する。この依存関係自体を「数式+LLM / 学習+LLM」の比較で観測対象にする。全件を LLM に流す構成は、コストの次元が変わって比較にならないため置かない。

## 配布形態: clone 参照型

PyPI 等のレジストリには出さない。これは再利用されるライブラリではなく実験とその結果が本体のリポであり、動かしたい人は clone して `uv run` すれば足りる。
