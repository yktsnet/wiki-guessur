# Method

[README](../README.md) の要約に対する全文。タスク定義とコーパス生成規模の詳細。

## タスク定義

- **素材**: Wikipediaダンプ（CC BY-SA）から自前生成する。記事名と本文のペアを取り、本文から自己同定の手がかり（冒頭の定義文）を除去する。
- **当てるもの**: 記事名1つと候補本文k件を与え、対応する本文を順位付けする。ダミー候補は、その記事名に言及している別記事（リンクグラフの被リンクから採取）を混ぜる。これにより「名前に言及する文書ほど正解ではない」という言及と同一性のねじれが自然に生じる想定だったが、実測ではねじれは逆向きだった（詳細は [design-decisions.md](design-decisions.md) の「完全一致ペナルティの棄却」）。
- **評価**: 1回の生成に対しては MRR。本体の評価軸はシードを変えて再生成したコーパス群での MRR の分布（平均・分散）。「一回当てられるか」ではなく「分布が変わっても当て続けられるか、再適応に何が要るか」を測る。

## コーパスの生成規模

1シードあたりの規模。

- **クエリ（記事名）**: 5,000件。
- **候補数k**: 2〜10件（被リンク数に応じて自然変動、平均8件程度）。
- **コーパス全体**: 記事約25,000〜30,000本（クエリの正解本文＋ダミー本文の和集合）。

根拠は3つ。IDF統計が安定する（数万本あれば文字n-gramの文書頻度が十分滑らかになる）、学習手法の訓練データとして足りる（クエリを train/test に割っても数千件ずつ残る）、再生成が軽い（1シード分の生成と全手法の評価がローカルで数分に収まる）。生成手順は、日本語版ダンプから被リンクが一定数以上ある記事を母集団とし、シード付き乱数でクエリをサンプリングする。被リンク条件を課すのは、ダミー候補が採取できない記事を最初から除くため。

## 比較の構造（2段階）

比較は「基礎スコアラー2種 × LLM再判定層の有無」の2軸で行う。LLM再判定は独立した手法ではなく、基礎スコアラーの上に載る層である（どのケースが僅差かを決めるのは下のスコアラー）。

**1段目: 基礎スコアラー（全件を順位付けする）**

1. **数式手法（人が係数を決める）**: 文字n-gram TF-IDFコサイン類似度。標準ライブラリのみ。係数は初回生成で手動フィットし、以後固定する（再調整しない縛りで、分布変化への弱さをそのまま観測する）。
2. **学習手法（機械が係数を決める）**: 完全一致有無・類似度・出現位置・密度・文書長などを特徴量化し、再生成のたびに train 分割で GBDT（LightGBM lambdarank）を再学習する。自動適応の代表。

**2段目: LLM再判定層（僅差ケースだけを差し替える）**

各スコアラーの上位2候補のスコア差が閾値未満のケースを判定対象とする。ただしAPIの無料枠の制約から、対象全件には回さず、対象の1/10程度をシード付きでサンプリングしてLLM判定し、そのサンプルでの正答率の改善から全対象へ適用した場合のMRRの伸びを推定値として報告する（サンプル件数を明記し、実測と推定を区別する）。

これにより比較は「数式のみ / 数式+LLM / 学習のみ / 学習+LLM」の4通りになり、LLM層の上乗せ効果が下のスコアラーの強さにどう依存するかも観測できる。

## 実装形態（CLI）

Python 製の CLI ツール。配布はせず、clone して `uv run wiki-guessur <subcommand>` で動かす参照型。パイプラインの各段をサブコマンドに対応させ、段の間はすべてファイルで受け渡す。あるサブコマンドの出力ファイルさえあれば、前段を再実行せずに後段だけ回せる。

- `fetch` — Wikipedia ダンプの取得。キャッシュディレクトリに保存し、取得済みなら何もしない。
- `generate --seed N` — コーパス生成。`corpora/seed-N/` に決定的に出力する。
- `eval --method {formula,gbdt} [--llm] --seed N` — 1構成×1シードの MRR 計測。
- `compare --seeds 0..N` — 構成×シードの MRR 行列を集計する。主要成果物。
- `diagnose --seeds 0..N` — 診断統計（言及率・候補数分布・ランダム基準）。
- `sweep --seeds 0..N` — 難易度ノブ（候補数上限）の掃引。
- `report` — 分布集計（平均・分散・シード内訳）を Markdown / CSV に書き出す。

コーパスは1シードあたり2ファイルに分ける。

- `queries.jsonl` — 1行1クエリ。記事名・候補文書ID群・正解文書ID。
- `corpus.jsonl` — 1行1文書。文書IDと定義文除去済み本文。

手法は `src/wiki_guessur/methods/` 配下に1ファイル1手法で置き、`eval` が `--method` 名で解決する。各手法は「クエリと候補群を受け取り順位を返す rank 関数」だけを公開する。

依存は、数式手法が標準ライブラリのみ（タスク定義上の縛り）、学習手法は LightGBM（lambdarank 目的関数を使う。縛りの対象外）、LLM 層は Gemini API クライアントとする。

## 制約

- 素材と生成過程はすべてWikipediaダンプ由来で自己完結させる。外部の問題設定・データを持ち込まない。
- LLM利用箇所はAPI前提で設計し、レート制限下でも部分適用で成立する構造にする（チャンク分割・フォールバック）。
